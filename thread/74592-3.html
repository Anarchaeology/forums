I may have found a solution. At least it fixed the problem for me.

For reference, I have Win XP, ATI 9700 Pro, 8x AGP, logitech cordless optical mouse, 768 MB RAM, athlon xp 2700+.

I found a similar problem noted on the web in a forum for another game (i don't remember the forum or the game). The tech's reply was to turn off tripple-buffering. His explanation was that with tripple-buffering on, mouse movement and character movement is only updated every 3 frames (or more, if the game is coded to update the mouse less often than every frame). Also, this would be more apparent the lower your framerate was (3 frames would take longer, so the mouse would update less often).

The thing that I don't understand about that explanation when applied to our problem in AO, is that the mouse lag would occur all the time, not just during nano particle effects. Maybe it's because frame-rate drops with the particles. I don't know; that's for you tech-heads out there, and you AO devs .

All I know is, I turned of tripple-buffering in the Open GL settings (does AO use Open GL for the "Hardware T&L capable device" option? (shrug)), and now I hardly notice any mouse lag with the nano effects.

A POTENTIAL ANSWER - THAT YOU WON'T LIKE AT ALL
Now, I'm not a programmer, but I am a software project manager, and here's my opinion, for what it's worth.

I believe the Slow-Mouse bug is a symptom of a significant memory leak in the AO Client software. I believe the leak is related to the 3D system, in particular that part of the system that hasn't been changed or updated in Notum Wars or Shadowlands, since this bug seems to have been around, in various forms for a long time.

I say this because the bug appears gradually for most people. You need to zone a few times (including zoning on dying) before it shows up. If you pass through a heavily populated zone (like OmniEnt BB, OA Hill, etc.) it's more likely to happen. As you know, every time you zone, you're removing one set of 3D objects and inserting another. Heavily populated zones have lots of extra 3D objects - all those different people in all their diverse outfits makes for a bigger 3D burden. Jobe also skirts the ragged edge of the 3D memory budget, and thus brings it on faster.

This kind of "slow degredation" issue is almost always the sign of a memory leak at work. Depending on exactly where the leak is happening, and what the compiler did, every time you try a fix and recompile, the problem seems to change a little. That's because almost any code change will cause the compiler to move things around some, resulting in slightly different malfunctions the next time.

As most of you know, relogging (logging out, then logging back in) generally corrects the bug. Relogging clears out all parts of memory devoted to AO, and restarts the program, thus erasing the mem leak effects, at least temporarily.

Needless to say, memory leaks are nasty to find and fix because what they're damaging is often "good" code. Trying to fix the bug by fixing the "good" code doesn't work, but in the process the programmers recompile, often moving the bug so it manifests in slightly different ways the next time.

Now, modern programming tools and methods include memory leak finding tools. However, you have to write your code according to certain rules to use these tools. I'll bet you dollars to donuts that FC wrote 3D code in a fashion incompatible with mem leak finders. Faced with such a situation you have three choices:

(a) Have a team of programmers perform a thorough code review of all suspect source code. This is extremely time-consuming and difficult, and only has a fair chance of fixing the problem, since you're betting the problem is evident by reading the source.

(b) Rewrite all suspect code in such a fashion that memory leak tools CAN be used. This often means rewriting a LOT of code, which can be very time-consuming and therefore costly. However, it will find and fix all mem leak problems, and probably a variety of others as well.

(c) Make random stabs at rewriting various code bits, in the hopes you'll get lucky and fix it. This is simple and quick, lets you pump up the "number of bugs fixed" each week, and gives the customer (we players) the feeling that something is being done. However, the chances of actually finding and fixing the real problem are virtually nil.

In a project a couple years back, after (c) had failed constantly, the customer signed on for a major upgrade, so we performed (b). In our weekly meetings the programmers almost always had gleeful expressions as they described how their rewritten code was finding and fixing all sorts of nastiness and evil. More often than not, they were saying, "Wow, I can't believe that code worked at all !!!"

My guess is that the transaction server was the one that crashed badly. I too lost a lot of implants and clusters (was in the middle of a new assembly).

Unfortunately, it looks like the way AO handles items being moved (from bag to inv, etc) is by the transaction server issuing temporary id's. I guess for performance reasons, these ids are cached in memory then flushed to disk at periodic intervals. So, if the computer running that transaction server crashes, it loses all the cached stuff. Short of spending millions for the transaction servers that credit card and airline companies use, there's probably no solution aside lowering the interval between flushes - but then that means everyone takes a serious performance hit whenever they move items around in the world (sometimes it already takes several secs for it to register).

And as for the 99.999% IT number, you still lose valuable data when that 0.001% chance the file server unexpectedly goes down. You lose everything in the buffer then.. like you lose it now.

I don't like it as much as the next guy, but you're paying $12 a month and you want the same level of *guarantees* (with better performance) as multimillion dollar clients? Just be glad you are at least guaranteed up until the last buffer flush.

Transactions, databases and data integrity happens to one of the areas I work with.

In any decent database ( I think FC uses Oracle, which should qualify. I think this due to a bug display in FC's pages at one time ), you have support for transactions. When you start moving things around in a database, changing structures, inserting dependant records etc, you normally start a transaction before you start the work. If something should fail during that transaction, you can do a rollback, effectively restoring everything as it was. Also, no real changes are done in the database until the transaction is committed.

Now, I know nothing of how FC has implemented their databases, but if they do NOT use transactions, they should be chased into a corner and repeatedly beaten with a soggy Leet doll

A decent database server is perfectly able to log each characters possession history for at least a week back. At least items that are not used up like bullets and kits...

Even a daily "snapshot" for a week back would help those who lose everything...losing 1 day should not be too bad for most characters.

If FC reads this, feel free to correct me on any assumptions I make. Also please review your database solution...

Seid,

Okay, I'm not the best person in the world to ask on IT transaction servers. So maybe you could help to see if there's any quick way to plug the holes in what I've seen.

To understand what can be done and what's acceptable by players, I think it might do well to look at how the AO transactions are laid out. Understand though, that this is an educated guess as to their server structure based on what's seen client-side.

Simple scenario with three server entities.. item, inventory, other (destination entity equip, playfield)

Player picks something up from the inventory on the client. This notifies the server side inventory entity and it relinquishes control of the item to the client. The inventory entity also informs the item entity at that said item is moving.

The player drops the item somewhere, whether it's on the playfield, equip pages, or bags. The client notifies the respective entity that the item is there now (after client checks requirements).

Now this is where the problem lies (I think). The destination entity can either contact the item entity and wait for confirmation and all that before responding to the client, or it can just respond back to the client first, and then check.

The first way is more secure. Duping would be impossible here since all items client side have an actual one-to-one correlation within that item entity. However, the downside is that it's slower. Especially considering that even the simple task of moving things between bags invokes this process, we could get peaks where the user would have to wait several seconds in the queue line.

The second way is what I think is actually being done. That is, the entity responds back that it accepts the item and that all is fine and dandy while it sends a request to the item entity for a final check. Only when it gets the final acknowledgement does it actually 'save' this into its database. This approach is more responsive client-side and you won't suffer from the 'item is stuck on my arrow' syndrome. The downside is that if something goes wrong (e.g. in-queue overflow or crash) with the system between the time the item was 'checked out' and 'checked in' on the item entity, then that item gets lost in limbo - it probably actually assumes it was a dupe item.

I guess they could try reconstructing items that are dangling (i.e. checked out but not in) but there might be a problem with playfield items for instance. Playfields are temporary and so should have these items been. If the item is restored but not the playfield, then the database starts accumulating garbage (i.e. items that no one is controlling).

Maybe if they haven't already, they can add a special tag to player-owned items and cross-corelate only those items with the individual entity dumps (from before the crash) to restore items every time the server crashes. But the system, in an attempt to avoid duping, is setup to treat inconsistencies as dupes. Something to consider when postulating solutions. It's a hard balancing act indeed.


I know, we're kinda doing their job but I don't care. And I know the above kinda comes across as being blow-hard, but I'd rather be more constructive in posting possible solutions instead of just perfect world scenarios. My head hurts just thinking about it though. Any other suggestions?
